## Goal
The routes the chat UI is built on (PLAN.md §11 row S4.2, reduced by rev 20 / D-084 to what the Streamlit UI needs): thread routes, and one route that takes a question and **streams** the answer. A little context: an answer takes seconds, so the server sends it as it is written. The wire format is server-sent events (SSE): one long HTTP response made of frames (`event: text` / `data: {...}` / blank line) that the client reads as they arrive. The server also builds, once at start-up, what answering needs (the retriever, the chat models, the warm-up), as the S4.1 log promised.

## Approved design (D-088)
The outline was given in chat at the start of the step (the user said "start S4.2"; prototyping mode builds right after the outline). The one addition beyond the plan row, flagged then: **citations persist** (below).

**New modules**
- `src/geekbot/sse.py`: `format_event(event, data)` (the ✍️ piece), `parse_events(lines)`, `parse_text(text)`, `SseEvent`. No imports from Geekbot, so the S4.4 client can use it without touching storage modules.
- `src/geekbot/server/answering.py`: `Answering` (the graph context built once, a way to make the chat model with `think` on, the warm-up that runs once), `TurnGate` (one question at a time), `open_chat_answering(settings, workspace, warm_up=True)`.
- `src/geekbot/server/turns.py`: `TurnTranslator` (graph stream events to SSE frames, keeps the last state), `describe_error` (an exception to the one sentence the `error` event carries).
- `src/geekbot/server/threads.py`: the router.

**Routes** (all under `/v1/threads`)
| Route | Result |
|---|---|
| `POST /v1/threads` | 201 `{thread_id: "t-<12 hex>", mode: "chat"}`; stores nothing |
| `GET /v1/threads?limit=50` | the newest threads that have an answered turn: id, mode, turns, message count, a one-line preview, taint, time |
| `GET /v1/threads/{id}` | the thread with its messages; each answer carries its sources (references, no passage text) and the `[n]` marks it cites; 404 if nothing was answered in it |
| `DELETE /v1/threads/{id}` | 204; 404; 409 while a question runs |
| `POST /v1/threads/{id}/messages` | body `{question, think=false}`; an SSE stream |

**The stream** (written out in the docstring of `server/threads.py`): `meta` (thread, turn, mode, model, think) at once; `status` (`loading_model`, only after `--no-warmup`); `text` and `thinking` pieces (already cleaned by G3 in the graph, passed on untouched except that the first piece of the answer loses its leading whitespace, as in the terminal); `done` (a `TurnOut`: the checked answer, the sources **with their passages**, citation marks kept and dropped, the checks, what the cleaning removed, taint, `searched_as` for a rewritten follow-up, retrieval stages, the readings of the model call); `error` (the last event, no `done` follows, **the client discards the shown text**). What can be refused before the stream is an HTTP error: 422 (bad thread name, empty / too long / malformed question), 409 (another question running; the thread belongs to another mode).

**Choices worth knowing** (each is in D-088)
- One question at a time, refused with 409, not queued. One chat model on one GPU; a thread's history is read-modify-write. Delete takes the same slot.
- The thread database is opened per call, as the CLI does (about twice per question: the pre-check and the turn), not kept open. Simpler and proven; a long-lived saver is the optimisation if the double open ever shows up in a measurement.
- A turn that failed or was abandoned leaves checkpoints without history. Such a thread is neither listed nor shown (404): nothing was answered in it.
- `SourceOut.text` is untrusted document text: the UI must show it as plain text, never as Markdown (it has not been through the answer filter).

## Watch for
- **Nothing was run, so every test is unproven.** Most likely to need a fix: ruff findings (I could not see them), mypy on the new LangGraph / aiosqlite typing in `runner.py::list_threads` and `stream_turn`, and the exact wording of one or two error messages the tests match (`json.loads` failure text, `allow_nan` error text).
- `test_healthz_stays_fast_while_an_answer_streams` is timing-based (p99 < 0.2 s with asyncio debug on, as S4.1's): if it flakes on a loaded PC, say so; do not loosen it blindly. It does a warm-up question first on purpose.
- `list_threads` queries the checkpointer's own table (`checkpoints`: `thread_id`, `checkpoint_ns`, `checkpoint_id`). `test_runner_threads.py` runs that against the installed `langgraph-checkpoint-sqlite`, so a later release that renames them fails there.
- `stream_turn` closes LangGraph's stream by hand when the consumer stops. `test_stopping_early_closes_the_stream...` and `test_closing_the_stream_early_gives_the_slot_back` cover it; a hang or a "Task was destroyed" warning there would be the sign of a problem.
- `--no-warmup` is for a busy GPU. Without it `geekbot serve` unloads the CSV model if loaded, loads the chat model (and the reranker on the CPU) before it listens: it takes seconds, and the server does not answer until then. After `keep_alive` (30 minutes) idle, Ollama drops the model and the next question reloads it (the `done` event's `generation.load_seconds` shows it, R-2).
