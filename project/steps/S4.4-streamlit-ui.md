## Goal
Give the server of S4.1 to S4.3 a face (PLAN.md §11 row S4.4): chat, knowledge, settings and evals pages in a browser, `geekbot up` to start it all, and the v1 files gone. A little context: Streamlit runs the whole script again on every click. v1 put its file uploader and its indexing in that script, so every click, a chat message included, indexed every uploaded file again (v1 bug #1, PLAN.md §5). So this UI is a thin client of the one process that owns the storage (§6.2), and nothing that costs anything can run on a plain rerun.

## Approved design (D-091)
The outline was given in chat at the start of the step; prototyping mode builds right after it. Nothing was asked of you.

**New: `src/geekbot/ui/`** (the folder is on `sys.path` when Streamlit runs `app.py`, so module names are chosen not to shadow a library: `client`, `display`, `views`)
- `client.py`: `GeekbotClient`, a synchronous `httpx` client. Sends the S4.3 key; `ping` (`/healthz`, no key), `health`, `formats`, `documents`, `upload` (raw body, with `Content-Length`), `ingest`, `delete_document`, `job`, `new_thread`, `threads`, `thread` (404 is `None`), `delete_thread`, `ask` (a generator of `SseEvent`: ends with `done` or `error`; a stream that stops before either raises `ServerUnavailableError`; closing it early closes the connection). `ApiError` carries the server's `detail` (FastAPI's list of validation messages is joined); `ServerUnavailableError` is "cannot reach, no key, stream broke". `connect(settings)` ends in one real authenticated call, because `/healthz` asks for no key and would say nothing about the key. `wait_for_job` polls with an injectable sleep and clock. Imports from Geekbot only `apikey`, `config` and `sse`.
- `display.py`: plain functions over the server's dicts, no Streamlit: `TurnView` (folds the events of a stream; on `error` it drops the live text, the S4.2 contract; the `done` answer replaces the pieces), `job_outcome`, `document_rows`, `state_counts`, `health_rows`, `source_header`, `thread_label`, `turn_details`, `human_bytes`, `one_line`.
- `views/chat.py`: the conversation is `?thread=<id>` in the address (and in the session, so Knowledge and back keeps it); a reload reads messages, source references and cited marks from the server; passages of an answer given in this session are kept in the session; a sidebar with new chat, "think harder", the thread list and a delete with a tick-box; a banner for an empty knowledge base or a cold model; the question is sent only from the chat input's own branch; the live answer is Markdown, a failed turn shows only the error; "Sources" (plain text, cited ones marked) and "Details" (model, times, what was changed) under a fresh answer; a CSV thread is shown and cannot be continued (C5).
- `views/knowledge.py` (**✍️, written by Claude**): see below.
- `views/settings.py`: read-only: the server's `/v1/health`, this UI's address and where its key came from (never the key), `mask_settings(Settings())`, and "edit `.env` and restart".
- `views/evals.py`: read-only: lists `.md` and `.json` files under `evals/results` (relative to where `geekbot up` was started), shows a report as Markdown and a JSON file as data (`st.json`); a file is read only if its real path is inside that folder and it is under 2 MB. It starts nothing (an evaluation loads models: GPU etiquette).
- `app.py`: `connect`, then `st.navigation` with the four pages; if the server cannot be reached or the key is refused the page shows one sentence and a "Try again" button. `main()` is behind `if __name__ == "__main__"` so tests can import the module.
- `launch.py`: the command `geekbot up` starts Streamlit with: `--server.address 127.0.0.1` (Streamlit listens on all interfaces by default; the UI holds the key and has no login), `--server.headless true`, `--browser.gatherUsageStats false` (telemetry off), `--server.maxUploadSize 95` (a little under the server's 100,000,000 bytes); the child's environment; start and stop of the child (terminate, kill after a grace period); `open_browser_when_ready`.

## Watch for
- **Nothing was run, so every test is unproven.** The likeliest fixes, in order: (1) **`ruff check` / `ruff format`**: I could not run either, and the default rule set is not one I can recite; a comment over 100 characters, a `PLR`, an unused import. (2) **`mypy src` on Streamlit's types**: `st.selectbox` returns an optional (I guard it), `st.query_params`, `type Placeholder = Any`, `st.status(...).update(state=...)`; if Streamlit's own type hints disagree with my reading, the fix is a cast at that line. (3) **`test_ui_pages.py` (AppTest)**: this project never used it. My guesses: `app.session_state[...] = fake` before the first run, `st.query_params` works inside a script test, `at.toggle`, `at.chat_input[0].set_value(...)`, `st.status` as a context manager, `st.rerun()` re-running the script, `Selectbox.select_index`, `st.file_uploader` rendering without an error. A failure there is as likely a wrong guess about `AppTest` as a wrong page; the failing line says which. (4) **`lint-imports`**: the contract lists external packages (`chromadb`, `langgraph`, `fastapi`, ...) and so needs `include_external_packages = true`, which is set; if it reports an unknown module, the name is the thing to fix. The `ast` test says the same thing inside `pytest`. (5) `test_the_browser_opens...` in `test_cli.py` waits up to 2 s for a background thread.
- **`test_streamlit_is_found_in_this_environment`** fails on purpose if `streamlit` is missing from the env (the two page test files are then silently not collected; this one is the loud signal).
- **A stream is abandoned by a click.** While an answer streams, any other click re-runs the script and the stream stops; the server sees the client go away and does not remember that turn. That is Streamlit's model; the page's docstring says so. Wait for an answer before clicking.
- **First start of Streamlit on Windows:** it may print its own banner and a firewall prompt may appear for `python.exe` (it binds to 127.0.0.1 only, so "private networks" or "cancel" is enough).
- `GEEKBOT_UI_PORT` / `--ui-port` and `--port` must differ; `up` stops with one line if they do not.

## Known gaps (stated, not hidden)
- **`geekbot up` and the UI were never started by hand** (nor were `serve`, S4.1 to S4.3). The checks above are the first time.
- A saved thread keeps only references to the sources of an answer; the passage text is shown only for answers given in this browser session (it is kept in the session, lost on a reload).
- The settings page does not write settings; the evals page runs nothing and reads `evals/results` relative to where `geekbot up` started.
- The UI process holds the API key in memory and Streamlit has no login of its own: it listens on 127.0.0.1 only, which keeps other machines out and not other programs on this PC, the same limit as the server's (S4.3).
- No keep-alive frames in the answer stream (S4.2): the client's read timeout is 5 minutes.
- CSV conversations (picker, upload, evidence view) are C5.
- `st.markdown` renders what the server's output filter let through; bare URLs in running text are not neutralised (a known limit of G3, D-086).
