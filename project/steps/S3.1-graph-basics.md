## Goal
`geekbot ask "…"`: a question goes through a fixed LangGraph, `retrieve` then `generate`, and comes back as an answer from the chat model, with the sources it was shown and the readings of the run (PLAN.md §7, §11 row S3.1). It is the first thing in the project that answers a question, which is why it comes before the ablation (D-068).

A little context. In an agent framework the model decides what to do next. Here nothing does: the edges are written down, the only decision is a plain function of the state, and the cost of a question is known in advance (one retrieval, at most one model call). LangGraph earns its place for what comes later in this phase (parallel branches, a checkpointer, retries), not for this one straight line. The part that is easy to get wrong is not the graph but the boundary around the model: the options it is called with must repeat the options it was warmed up with (R-2), the prompt must be built in exactly one place (§8.2), and a failure of Ollama must reach the user as one clear line.

## Approved design
Outline given in the chat of 2026-10-17 and accepted ("looks like I'm ready let's go"). Decisions: D-069. Changes during the build: none to the outline; `search` was refactored onto the new retriever factory (stated in the outline).

- `agent/state.py`: `AgentState` (plain data, `total=False`) and `SourceRef` (a numbered source record).

- `agent/packing.py`: `pack_prompt`, the only place a prompt is assembled; minimal now, extended in S3.2.
- `agent/nodes.py`: `retrieve`, `has_sources` (the one conditional edge), `no_context`, **`generate` (the ✍️ piece)**, and helpers `message_text`, `generation_stats`, `source_refs`.
- `agent/graph.py`: `build_graph()`; `agent/render.py`: `format_answer`, `format_prompt`.
- `llm/chat.py`: `make_chat_model` (a `ChatOllama` built from the settings), the `ChatModel` protocol, `ChatError`.
- `retrieval/factory.py`: `build_retriever(mode, workspace, settings, candidates)`; `SearchMode` moved to `retrieval/__init__.py`. `geekbot search` now uses the factory.
- `config.py`: `chat_num_predict` (512), `chat_temperature` (0.2), `context_budget_tokens` (3000); `.env.example`.
- `cli.py`: `geekbot ask QUESTION [--top-k 5] [--mode hybrid_rerank] [--candidates 50] [--show-prompt]`.
- `pyproject.toml`: `langgraph>=1.0`, `langchain-core>=1.0`, `langchain-ollama>=1.0`.

**Where this differs from the plan's row:** `packing.py` is S3.2's file in the plan; a minimal version arrives here so that even the first prompt is assembled in the one permitted place. S3.2 extends it (prompt files, data-marking, labels, `[n]` validation).

**Observations (one machine, one run each, `proto` profile; plumbing, not SLO measurements):**
- *The first real request after the warm-up was slow.* The call took 5.93 s for 40 output tokens (decoding 40 tokens at 157.5 tokens/s is 0.25 s), while the next question in a new process took 0.40 s for 10 tokens with a prompt of similar size. The model was already loaded in both (load 0.01 s and 0.00 s). The difference is consistent with a one-time cost on the first inference that the empty-prompt warm-up does not pay. S3.3 should measure it and consider warming up with a real one-token generation.
- *Retrieval took 26.0 s on the first run and 1.8 s on the second.* The first included downloading the 86.8 MB reranker; of the second, 1,770 ms was the `rerank` stage, which in a fresh process includes loading the ONNX model. A warm server will not pay the load; `geekbot rerank-timing` measures the scoring alone and has not been run on this corpus yet.

## Open issues / follow-ups
- **Settled by the runs:** `langchain-ollama>=1.0` resolves (1.1.0); Ollama accepts `reasoning=False` for `gemma3:4b`; the metadata keys are the ones `generation_stats` reads; LangGraph runs the context dataclass and the `Runtime` argument as documented. Still unverified: `reasoning=False` on `gemma4:12b` (target profile), and every number above on the target models.
- **For S3.2:** the source header repeats the document title when the heading trail starts with it (seen on the FAQ: "Lantern staff FAQ | Lantern staff FAQ > Your conversations > ..."). Drop a leading section element equal to the title, in the data (`source_refs`), so the prompt and the printout both lose it.
- **For S3.5:** when the model says it could not find the answer, `ask` still prints five sources under it, which suggests they support something. Abstaining should drop them.
- **For S3.3:** the first-request cost after the warm-up (above), and the cold-process rerank time (above).
- **Privacy, to keep an eye on:** `langchain-core` brings `langsmith` with it (pytest even lists a `langsmith` plugin). It sends nothing unless tracing is switched on with `LANGSMITH_*` / `LANGCHAIN_*` environment variables and a key. Do not set them; a `doctor` check that fails when one is set would make the rule enforceable (not built).
- **Cosmetic:** Windows prints a Hugging Face "symlinks not supported" warning on the first reranker download, and the download's progress bars interleave with the answer that first time.
- **Known gaps by design:** no citation check (S3.2), no streaming (S3.3), no memory (S3.4), no abstain beyond "nothing retrieved" (S3.5), retrieval strictly sequential (S3.6). Retrieval defaults (hybrid with the cross-encoder, 50 candidates, depth 30, top-k 5) are starting points until S2.6.
- **For S3.4:** the state holds plain data on purpose (`SourceRef` dicts, not `Chunk` objects), so a checkpointer can save it. Check that before relying on it.
- **Security, stated:** until S3.2 (data-marking) and S3.5 (the output filter) a poisoned document can still steer the answer and the answer can contain markdown the terminal prints as text. `ask` is a terminal command; the server and UI (Phase 4) must not render the answer before G3.
