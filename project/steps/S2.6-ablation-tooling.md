## Goal
Measure retrieval quality with one change per step, so that every claim about the pipeline ("hybrid beats dense", "the header helps", "the reranker is worth its 300 ms") is a number with its interval and not an opinion (PLAN.md §9, §11 row S2.6). The tooling has to exist, be tested and be reviewed before any number is produced: the choices in D-079 are written down first so none can be adjusted afterwards to flatter a result.

A little context. An ablation is a ladder: start from the old system, change one thing, measure, change the next thing, measure. The ladder here starts from a replica of v1 (R0) and ends at the full v2 pipeline (R7). It answers "how much did each part add *given what came before*"; the leave-one-out runs answer "how much does each part add *given everything else*". They can disagree when two parts overlap (a reranker can make BM25 less necessary), which is why the plan asks for both. The gotcha: the unit of comparison. If a system returns ten *chunks* and the metric counts *documents*, then smaller chunks cover fewer documents, and the "new chunking" rung quietly includes that effect. The report prints documents per query beside every score so the effect is visible.

## Approved design
See D-079 for the choices and PLAN §9 for the plan. In files:

- `evals/ablation.py`: the rungs (`RUNGS`), the leave-one-out variants (`LEAVE_ONE_OUT`), the index variants, and the TOML configuration (`AblationConfig`, `load_config`; unknown keys are errors).
- `evals/legacy.py`: R0. v1's chunker (LangChain's splitter, imported lazily) and v1's multi-query retrieval.
- `evals/indexing.py`: builds one index variant from loaded documents into a scratch folder (batched embedding, a shared cache, a marker file so a finished build is reused); BEIR documents.
- `evals/runner.py`: a rung's strategy becomes a retriever; a question set runs through it with the clock and the CPU gate around the loop; per-question scores; the result record; a memoizing scorer for the sweeps.
- `evals/phases.py`: the phases (ablation, tuning, bakeoff, abstain), dataset bundles, resumable result files.
- `evals/orchestrate.py`: which bundles go to which phase, the order, the rewrite phase.
- `evals/rewrites.py`: the cached rewrites of golden follow-ups (D-076).
- `evals/cpugate.py`: the CPU gate (D-078) as code.
- `evals/report.py`: the Markdown report from the result files.
- `retrieval/calibrate.py`: **the ✍️ piece**, the abstain-threshold calibration.
- `index/dense.py`: `DenseIndex(space="cosine" | "l2")`.
- CLI: `geekbot eval retrieval --config evals/configs/ablation.toml [--phase ...] [--rung ...] [--dataset ...] [--fresh]` and `geekbot eval report`.
- `evals/configs/ablation.toml`: the run's configuration.

Changes made during the build, and why: the pytest settings gained `pythonpath = ["tests/unit"]` (importlib mode cannot import the shared fakes in `tests/unit/evalkit.py`); the test fake embedder was widened from 64 to 512 dimensions after a hash collision made a toy ranking wrong; `evals/orchestrate.py` and `evals/phases.py` were split so the command-line function stays thin.

## Review + walkthrough Q&A
Spots to review, in order of where a mistake would matter most:
1. `evals/legacy.py`: is R0 really v1? (CP2's v1 run compares the chunks and the golden Recall@5.) The splitter is the 1.x package, not 0.3.11.
2. `evals/runner.py::record_of` and `evals/report.py`: the Holm family (`HOLM_FAMILY`) and which comparisons get a p-value.
3. `evals/phases.py::run_abstain`: the signal is the best chunk's rerank score; multi-turn items without a cached rewrite are left out and counted.
4. `evals/indexing.py`: the build reuses an index when the embedder fingerprint and the document count match; a *changed document with the same count* would be reused wrongly. Scratch folders are the evaluation's own, so this matters only if someone edits the corpus between runs; `--fresh` plus deleting `scratch/ablation` is the remedy.

Results: `evals/results/s26-run1/{rewrites,ablation,tuning}.json` and the generated `report.md`. The headline numbers and what they say are in STATUS.md "Measured results so far" and in the report; this log does not repeat them. All 40 timed ablation sections and the 9 latency sections of the sweep were read as idle by the CPU gate. The golden numbers were the same in two separate runs (a smoke run before the tooling was committed and the real run), so the quality numbers are repeatable.

What to look at first, because it is surprising: the reranker (MiniLM, depth 10) did **not** improve nDCG@10 on SciFact (−0.0250 [−0.0455, −0.0042]) or NFCorpus (+0.0010 [−0.0078, +0.0094]), and improved it on golden test (+0.0512 [+0.0172, +0.0895]) but not on golden dev. Nothing in the pipeline was changed after seeing this (the sweep, the config and the code were fixed before the run, D-079). Possible reasons are not tested here: MiniLM-L-6 is trained on web questions and passages, SciFact and NFCorpus are scientific and nutrition text; only the top ten fused chunks are re-ordered, so it can lose a good hybrid ranking but cannot add a missed document; golden v0 documents are short and written in the same plain style as its questions. The reranker bake-off (part 3, bge-reranker-base) is the next piece of evidence.

Also for you: the plan's 400 ms p95 target for retrieval plus rerank holds on the golden corpus (375 to 400 ms) and does not on BEIR's longer abstracts (528 to 626 ms at depth 10). The depth sweep gives no quality reason to go above 10 on BEIR (differences within 0.013) and a small one on golden dev (+0.03 at depth 30 for about three times the time). The default depth stays 10 (D-077); that decision is yours.

## Phase look-back (Phase 2: S2.1 to S2.6)
- **Planned vs actual:** six steps. S2.4 (the golden set) was split in two and finished late because it needs data, S2.5 was built before it, S2.6 moved to after S3.4 (rev 19), and S2.6 itself became three pull requests (tooling, ablation and sweeps, bake-offs). The plan's single row for S2.6 hid the size of the job: about 5,200 lines of code and tests, and about 7.5 hours of wall-clock time on the user's PC (embedding is the cost: 5 chunks per second for the v2 chunks, 1 per second for `qwen3-embedding:0.6b`).
- **Surprises:** (1) the reranker did not help on BEIR and the plan had it as the last and largest rung; (2) rung R2 (dropping the template multi-query) is the biggest single gain, so most of the distance between v1 and v2 is something v1 did wrong (five queries and a re-sort by re-embedding) and not something v2 added; (3) the abstain signal the plan assumed (a threshold on the reranker's score) is weak on golden v0; (4) the 400 ms retrieval target holds on the small golden corpus and not on BEIR's long abstracts; (5) the embedding time of the bake-off (a qwen3 index took 1.5 hours) is the reason a bake-off is better done once and cached.
- **What went well:** deciding every analysis choice before any number existed (D-079); the resumable result files (a three-hour run could be left alone); the CPU gate (no timed section was lost to background load, unlike two earlier timing sessions); a real smoke run before the commit that found the tooling worked end to end; the held-choice reruns that reproduced the ablation exactly.
- **What to change:** the golden set is too easy and too small to separate systems (32 development and 48 test questions, one author; every golden interval is wide), so the user's own questions matter more than any further tuning; the `docs/query` confound is a design weakness (a document-level k would be cleaner) and should be revisited if the ladder is reported outside this repository; the per-phase wall-clock times should be written into the config's comments before a run so the next one can be planned.
