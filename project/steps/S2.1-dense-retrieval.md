## Goal
Given a question, find the chunks whose meaning is nearest, and show them with their similarity and how long each stage took (PLAN.md §11 row S2.1): `geekbot search "…"`.

A little context. Dense retrieval compares *meaning*: the question and every chunk are vectors, and the closest come first. It finds "how do I cancel my subscription" in a chunk that says "ending your plan", with no shared word, which BM25 cannot. The catch is that Chroma only knows vectors. Whether a chunk may be shown (its document is `ready`) is SQLite's knowledge, so every hit goes back through SQLite, and the search must keep asking Chroma for more candidates when it drops some, or it would return fewer than `k` results while ready chunks exist.

## Approved design
Fast-prototyping mode (D-047): the outline was this plan, covered by the standing delegation of the overnight run (D-057). Decisions: D-060.

- `retrieval/__init__.py`: `Retriever` (`search(query, k) -> RetrievalResult`), `RetrievalResult` (chunks best first, `timings_ms`), `format_result`.
- `retrieval/dense.py`: `resolve_hits` (the ✍️ piece) and `DenseRetriever` (embed the query, query Chroma, resolve through SQLite, over-fetch ×4 until `k` survive or the index is exhausted).
- `cli.py`: `geekbot search QUERY [--top-k N] [--mode dense]`; the other modes exit 2 as not built (S2.2, S2.3).
- No change to the stores: everything needed (`DenseIndex.query`, `Store.get_chunks`, `CachedEmbedder.embed_query`) came from S1.4 to S1.6.

**Changes during the build:** none to the design. The timing test first expected 4 ms and the code reports 5: five clock calls, one millisecond apart (start, after embedding, around the search and the resolve, the end); the test was wrong, not the code.

## Open issues / follow-ups
- Whether `nomic-embed-text` returns unit-length vectors (the R1 expectation) is still unmeasured; Chroma's cosine space does not need it.
- The chunk, not the document, is the unit returned. BEIR scoring aggregates chunk hits to documents by max (PLAN §9); that belongs to the eval code (S2.5, S2.6).
- `geekbot search` takes the storage lock, so it cannot run while `geekbot serve` (S4.1) owns the data folder; the server will expose the same retriever over HTTP.
