## Goal
Split each loaded document into the pieces that get embedded, searched and cited: about 512 tokens with 64 tokens of overlap, each knowing its page, its heading path and its exact position in the document (PLAN.md §6.4, §6.6, §11 S1.2). The size is where the ablation's rung R4 starts (§9); the contextual header is rung R5.

## Design (fast-prototyping mode, D-047: outline given in chat, then built; recorded as D-053)
**One question put to the user, answered:** hand-written splitter or LangChain's `RecursiveCharacterTextSplitter`. The user chose **hand-written** (Claude's recommendation). Reason: LangChain's splitters return text without positions, and recovering them with `str.find` is ambiguous when a passage repeats; the plan needs `char_start` / `char_end` for citations, and an exact "no text is lost" test. This corrected PLAN §6.4's wording (rev 17).

**Shape of the result** (`ingest/chunking.py`): `chunk_document(doc)` returns a list of `ChunkDraft`s: `text`, `char_start`, `char_end` (offsets into `LoadedDocument.text`, so `doc.text[start:end] == text`), `page` (1-based or `None`), `section_path` (headings above it), `header` (`title > heading > subheading`), `ordinal`. No ID yet: S1.3 adds `doc_id`, `content_hash`, `occurrence` and `chunk_id`.

**Three passes per segment** (a segment is a PDF page, a slide, or the whole file):
1. **Sections.** Only Markdown-like kinds (markdown, docx, pptx, html, notebook, table card) are cut at their `#` headings. A `#` line inside a code fence is not a heading. A heading with nothing under it joins the next section (a document title followed straight by its first part). Text before the first heading has an empty path. Plain text and code are never read for headings, because `# ...` there is a comment.
2. **Pieces.** A section is cut at the coarsest boundary that makes the parts fit: paragraph, line, sentence, word, and as a last resort fixed runs of characters. Code first cuts at declarations: Python (decorators stay with their `def`; methods inside a class), Ruby, JS, TS, Go, Rust, and a generic rule (a line starting in column 0 that is not a closing bracket) for the other languages S1.1 names.
3. **Windows.** Pieces are merged left to right up to 512 tokens. The next chunk reopens with the last pieces that fit in 64 tokens, but never so many that the next piece no longer fits beside them (otherwise the next chunk would only repeat the last one).

**Choices worth knowing**
- *A chunk never crosses a page or a heading.* A citation always has one page and one heading path; the price is small chunks where a section is short (a two-line section is a two-line chunk).
- *Tokens are estimated, not counted.* `estimate_tokens` counts one token per five letters or digits, one per CJK character, one per punctuation mark, none for whitespace. It over-counts a little on purpose and never exceeds one token per character. The embedder's real tokenizer arrives at S1.5, where a live test compares the two (Ollama's `/api/embed` returns `prompt_eval_count`); until then "512 tokens" means 512 estimated tokens.
- *The header is stored beside the text,* not inside it (`embedding_text(with_header=...)`), so rung R5 changes the embedder's input without changing the chunk or its future ID. **S1.5's embedding-cache key must therefore cover the header mode.**
- *Whitespace.* Blank lines before a chunk and whitespace after it are trimmed; the indentation of the first line stays (code). A chunk that would lie wholly inside the previous one (it adds only whitespace) is not emitted.
- *Overlap runs across every kind of boundary,* because pieces from all levels are merged in one pass; LangChain merges per level and only overlaps inside one. Simpler to reason about, and the property tests pin it down.
- *Untrusted input.* A line over 300 characters is never a heading, which also keeps the heading pattern cheap on a hostile line.
- *`SEGMENT_SEPARATOR`* (`"\n\n"`) is now a constant in the loaders' `model.py`, used by `LoadedDocument.text` and by the chunker's offsets, so they cannot drift apart.

## Things I could not check without running (what to watch)
_Resolved by the user's run (reported all good, details not pasted); kept as the record of what was assumed._
Everything below was reasoned by hand, not observed; nothing was run by Claude (no-run policy).
- **The hypothesis tests are the likeliest place for a first failure.** They throw arbitrary text at the chunker. If one fails, hypothesis prints the smallest failing input; paste it. The ordering test (starts never decrease, ends strictly increase) and the overlap-size test rest on the longest hand arguments.
- **Regex behaviour:** the `\uXXXX` ranges are written with doubled backslashes (`_CJK`, `_SENTENCE`) so the file stays ASCII; the regex engine reads them as Unicode escapes. If `estimate_tokens("漢字。") == 3` fails, start there.
- **The example tests assert exact token arithmetic** (for instance eight tokens per "Sentence number N is here." and nine per tiny Python method). A failing count points at `estimate_tokens` or at my arithmetic in the test.
- **The `sales_small.csv` card test** assumes the card's only `#` line is its title.
- **ruff:** formatting was done by hand; `ruff format .` first, as at S1.1. Possible lint hits: long lines near 100 characters, import order in the test.
- **mypy:** `Callable` stored in a frozen dataclass field (`_Budget.count`) is called as `budget.count(text)`; strict mode should accept it.
