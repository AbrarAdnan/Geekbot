## Goal
Give Geekbot one place that holds what was ingested, and the first way to search it (PLAN.md §6.2–§6.4, §11 S1.4). SQLite is the source of truth: documents, chunks, and an FTS5 full-text index over the chunk text. Chroma (S1.5) will be a derived index that can be rebuilt from it. This step also enforces the plan's storage invariant: exactly one process owns the stores.

## Design (fast-prototyping mode, D-047: outline given in chat, then built; recorded as D-055)

**What was built**
- `index/lock.py`: `StorageLock`, an exclusive `filelock` on `<data_dir>/.storage.lock`. It never waits: a second holder gets `StorageLockedError` at once. The lock is shared by all threads of the process and is not re-entrant. The OS drops it when the process dies, so a crash leaves nothing to delete.
- `index/sqlite.py`:
  - `Store(data_dir)` takes the lock, opens `geekbot.db` in WAL mode and applies the migrations. `close()` or `with` releases everything. A store that fails to open releases the lock.
  - *Writes* go through one writer thread (a single-worker `ThreadPoolExecutor` is the queue). Each runs in `BEGIN IMMEDIATE ... COMMIT` and is rolled back if it raises. *Reads* borrow one of four read-only (`query_only`) connections and see one consistent snapshot; a read never waits for a write. The store is synchronous on purpose: the server (S4.1) calls it through `anyio.to_thread.run_sync` (§6.3).
  - Migrations: a numbered list, applied in order, each in one transaction together with the `PRAGMA user_version` bump. A database from a newer Geekbot is refused. Migration 1 creates `documents`, `chunks`, the FTS5 table `chunks_fts` and three triggers.
  - Documents: `upsert_document`, `set_document_state`, `get_document`, `delete_document`.
  - Chunks: `sync_chunks` (re-ingest as a set difference on `chunk_id`), `get_chunks`.
  - Search ✍️: `fts_match_query` and `search_bm25`. Plus `rebuild_fts` (derived data, always safe to rebuild).
- `domain.py`: `NewDocument`, `Document`, `Chunk`, `ScoredChunk`, `DocState`. Plain data, so ingest, index and retrieval share records without importing each other.

**Choices worth knowing**
- *`chunks.row_id` is an explicit `INTEGER PRIMARY KEY`, separate from `chunk_id` (`UNIQUE`).* FTS5's external-content link needs an integer that never changes. The hidden rowid of a table keyed by text may be renumbered by `VACUUM`, which would silently break the link.
- *External-content FTS5 and its triggers.* `chunks_fts` stores the index but not a second copy of the text. The price: we keep it in step with three triggers, and the 'delete' command needs the **old** values (`old.text`), or the index is corrupted. The update trigger fires on `UPDATE OF text` only, so a pure move (S1.3: position columns are rewritten in place) never touches the index. `sync_chunks` keeps `text` out of the `SET` list for a move.
- *Only the chunk text is indexed, not the header or the section path.* The ablation's header rung (R5, §9) must change what the embedder sees and nothing else. A header that BM25 always saw would make "−header" a two-variable change.
- *Tokenizer `porter unicode61 remove_diacritics 2`:* case and accent folding plus English stemming ("returns" finds "returning"). Limits: stemming is English-only, and a run of CJK characters is one token, so Chinese, Japanese and Korean text is poorly searchable lexically. Changing the tokenizer later is a migration plus `rebuild_fts()`.
- *Ready-only is in the same SQL statement as `MATCH` and `LIMIT`.* The limit therefore counts ready chunks: a query never comes back short because the best hits belonged to a pending file. `upsert_document` puts a document back to `pending`, so **an edited document is invisible to retrieval while it is re-processed** (§6.4's rule, with that price).
- *`sync_chunks` returns four lists of IDs:* `added` (to embed), `removed` (vectors to drop), `updated` (kept, text or position changed), `unchanged`. A text-only difference the ID ignores (trailing whitespace, line endings) updates the stored text, because the offsets must keep pointing at the exact slice of the file.
- *The query builder.* `fts_match_query` cuts the typed text into words, double-quotes each one, and joins them with `OR`: `refund policy?` becomes `"refund" OR "policy"`. Quoting makes `AND`, `NOT`, `NEAR(`, `col:term`, `*`, `^` and unbalanced quotes plain words instead of FTS5 syntax. OR (not AND) because a question has words the right chunk need not contain, and BM25 down-weights common words by itself. Repeats are dropped, and at most 64 words are kept.
- *Scores.* FTS5's `bm25()` is "lower is better" (k1 and b are fixed by SQLite); `search_bm25` returns `-bm25`, a positive number where higher is better, comparable only within one query. Ties (identical chunks tie exactly) are broken by `chunk_id`, so a ranking is the same on every run.
- *Statement-level safety:* IDs are passed to SQL as one JSON array parameter (`json_each(?)`), so no SQL is built from strings and there is no limit on the number of IDs.
- *`file_hash` and `pipeline_version` are columns of `documents`* (S1.3's handoff: "skip unchanged" keys on both). Anything else S1.6 needs is a later migration, which this step's machinery supports and tests.

## Things I could not check without running (what to watch)
Everything below was reasoned by hand, not observed; nothing was run by Claude (no-run policy).
- **FTS5 external-content details are the likeliest first failure.** A message like "database disk image is malformed" or a search that finds a deleted chunk would mean a trigger passed the wrong old values. The model-based property test (`test_search_always_agrees_with_a_model_of_what_is_stored`) and `test_a_change_the_id_ignores_still_updates_the_stored_text` exercise the insert, delete and rewrite paths; hypothesis prints the smallest failing pair of chunk lists.
- **`filelock` 4.2.0 is the version in the lock;** the code uses the API of 3.x (`FileLock(path, thread_local=False)`, `acquire(timeout=0)`, `Timeout`, `is_locked`) and assumes 4.x kept it. `test_a_second_lock_on_the_same_directory_is_refused_at_once` also assumes the OS refuses a second lock handle on the same file inside one process (true for Windows byte-range locks and POSIX `flock`); the cross-process test does not depend on that.
- **The search expectations were computed by hand** from BM25 on the eight-sentence corpus ("refund" ranks chunk 2 above chunk 0; the word "the" has a negative IDF, which FTS5 clamps to a tiny positive number). If a ranking test fails, paste the scores it printed.
- **`ORDER BY score` uses the alias of `bm25(chunks_fts)` in a join.** This is the documented usage with a plain `ORDER BY bm25(...)`; the alias should behave the same.
- **A character that Python calls a letter but this SQLite's Unicode tables do not know** would make a quoted word tokenize to nothing. I believe FTS5 treats an empty phrase as "matches nothing" and raises no error; the property test `test_any_text_makes_a_query_that_fts5_accepts` is the check.
- **mypy:** PEP 695 generic methods (`def write[T]`) and `Sequence[Any]` rows should pass strict mode. **ruff:** the 0.16 default set is large; possible complaints are argument counts, a long line, or an unused fixture argument (I used `usefixtures` for those). Run `ruff format .` first.
- **Not tested:** a chunk text with a lone surrogate (Python's `sqlite3` raises `UnicodeEncodeError` on insert, so that document would fail whole; S1.6's per-file report should catch it); CJK search quality; a power cut or crash in the middle of a write; running out of read connections (the 30 s wait); the foreign key's cascade (deletes are explicit); performance on a large corpus (no number is claimed).
