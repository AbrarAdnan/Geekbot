## Goal
Finish what PLAN §7 draws for the answer graph and PLAN §11 names for this step: the dense and the lexical search side by side (`dense ‖ lexical → fuse → rerank`), a `RetryPolicy` on the steps that call Ollama, step events from the nodes, and a live smoke test of the latency targets of §6.5. A little context for this step:

- **The expected gain is small, and the step is built to find out.** BM25 takes a few milliseconds and the dense search tens (an embedding call to Ollama on the CPU, a Chroma query). Running them together saves at most the shorter one, and every extra graph step costs a thread hop and a saved checkpoint. So the parallel schedule ships with an off switch (`GEEKBOT_PARALLEL_SEARCH=false`) and with a live test that times both schedules in one process, interleaved. No speed claim is made here.
- **A retry is a decision about which errors, not "try again".** LangGraph's default retry predicate never retries a `RuntimeError`, and everything this program raises on purpose is one. And a streaming answer has a trap: if a stream breaks half way and the step runs again, the whole answer is written a second time under the half that is already on the screen.
- **The graph state is saved after every step and every checkpoint is kept.** Two lists of fifty chunk texts would be written to `threads.db` over and over. The state therefore carries candidate *IDs* between the stages, and only the last stage reads text.
