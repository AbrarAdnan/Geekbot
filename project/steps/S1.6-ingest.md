## Goal
Join everything Phase 1 built into one command: `geekbot ingest <files or folders>` turns files into searchable documents (PLAN.md §6.4, §11 row S1.6), and `geekbot doctor --repair` fixes what a crash leaves behind.

A little context. A document lives in two places, SQLite (the rows) and Chroma (the vectors), and no operation can change both at once. The **outbox pattern** is the answer: write the order down (`pending → embedding → ready`), do the steps in that order, and let only `ready` documents be searched. A crash then leaves a document that nobody can retrieve and that a repair can finish, never one that is half-visible. The state is the repair's memory of how far the ingest got.

## Approved design
Fast-prototyping mode (D-047): the outline was this plan, covered by the standing delegation of the overnight run (D-057). Decisions: D-059.

- `ingest/outbox.py`: `ALLOWED_MOVES` (seven edges), `check_move` (pure; the ✍️ piece), `Outbox` (`begin`, `move`, `fail`) over `Store.transition_document` (an atomic compare-and-set).
- `ingest/jobs.py`: `parse_file` / `parse_files`, a spawn process pool with a bounded window; workers never touch storage.
- `ingest/pipeline.py`: `collect_files` (folder walk), `pipeline_version`, `Ingestor.ingest` (skip unchanged → parse → record → sync rows → embed → ready; per-file failure), `Ingestor.remove`, `FileOutcome`, `IngestReport`.
- `index/vectors.py`: `write_document_vectors`, the shared "make the vectors match the rows" routine.
- `index/consistency.py`: `check_consistency`, `repair` (state table in its docstring).
- `index/workspace.py`: `Workspace.open` opens store, embedder, dense index and cache in the right order and closes them in reverse.
- `cli.py`: `geekbot ingest PATHS... [--workers N] [--reindex]`, `geekbot doctor --repair`.
- `Store`: `transition_document`, `list_documents`, `document_chunks`, `chunk_ids_by_document`, `StateConflictError`.

**Changes during the build:** none to the design. The lone-surrogate test showed the failure happens at the SQLite insert (the hash is fine), so the document is recorded as `failed`; the test was corrected to say so. `ruff` wanted the four deliberate broad `except Exception` blocks marked (`noqa: BLE001`, each with its reason): a bad file must be a result, never a crash.

**One refinement of S1.4's handoff, flagged for review.** The handoff said to embed exactly `ChunkSync.added`. The pipeline embeds every chunk of a processed document through the cache instead (D-059 point 3): the same cost in the normal case, and correct after a crash that left vectors unwritten, after a wiped Chroma, and after a heading rename above an unchanged chunk.

## Open issues / follow-ups
- The plan's check "ingest `evals/corpus` twice, the second run embeds 0" needs the corpus (the user curates it, D-032). Command: `geekbot ingest evals/corpus` twice, in the `geekbot` env, with Ollama running and `nomic-embed-text` pulled; the second summary line must say `0 embeddings computed`.
- `geekbot doctor` (without `--repair`) does not check the embedder yet: model pulled, running on the CPU.
- No CLI command removes a single file; `Ingestor.remove` exists and is tested. A file deleted from disk stays in the store until that command exists (S4.4's knowledge page is its natural home).
- Nothing yet detects that the *chunk text* of a stored document differs from what the file would produce today; only the file hash and the pipeline version trigger a re-process (by design).
- `ingest --workers N` was tested with 2 workers on small files; its speed-up is unmeasured.
- A model-based test of the repair under random crashes would be stronger than the three crash cases written.

## Phase look-back (Phase 1: S1.1 to S1.6)
- **Planned vs actual:** six steps, one chat each, as planned; S1.4 and S1.6 were the largest. The plan's row for S1.6 named five pieces (`pipeline.py`, `jobs.py`, `consistency.py`, `geekbot ingest`, `doctor --repair`) and all five exist, plus two the design needed (`vectors.py`, `workspace.py`).
- **Surprises:** (1) the embedding-cache key had to include the header, which the plan's wording missed (D-058); (2) the right unit of "needs vectors" is the whole document through the cache, not the added chunks (D-059); (3) a repair must never mark a `pending` document `ready`, because the new file hash is already stored (D-059); (4) Windows CI is slow once Chroma's dependencies are in the lock (about 25 minutes for the first run).
- **What went well:** every invariant in §6.4 now has a test, and the two stores are checked against each other (`assert_in_step`) after every ingest in the tests.
- **What to change:** the golden corpus is the first thing Phase 2 needs and does not exist; S2.1 can be built and unit-tested without it, but no retrieval number can be reported before it does.
