## Goal
PLAN §9 "Bench" and "gemma4 tuning sweep", PLAN §11 row S5.1: measure what the product costs on the target models (time to first token, tokens per second, retrieval, ingest speed, VRAM, residency, load events, other GPU users), sweep the settings (`num_ctx` x KV-cache type x `num_batch` x top-k, plus thinking on and off as information), add the CSV-mode rows, and record numbers **only when the GPU is idle**. "The default is the best quality that meets all SLOs at 100% residency." Every number in the README must be regenerable with one command from `evals/configs/*.toml`.

A little context:
- **The KV-cache type is a server setting.** `OLLAMA_KV_CACHE_TYPE` and flash attention belong to the Ollama server, not to a request, so sweeping them means restarting the server, and the server on port 11434 is yours (other programs use it). The sweep therefore starts **its own Ollama on port 11435** with the settings it needs, on the same model files, and stops it (the whole process tree) afterwards. Your server is never restarted or reconfigured.
- **`num_batch` is a load-time option, like `num_ctx`.** Ollama reloads a model whose request carries a different one (R-2). LangChain's `ChatOllama` has no field for it, so a small subclass adds it to every request, and the warm-up sends it too; with `chat_num_batch` unset nothing changes.
- **A guard that cries wolf is no guard.** The first live run of the idle-GPU guard called the PC busy because on Windows the driver lists every program with a window (21 of them: the shell, a browser, a chat client, a game launcher ...) as a "compute process". Memory and utilisation decide now; the process list only names who may be using the card when one of those already says busy.
- **Noise is the enemy of "best quality".** With 8 questions asked 3 times each one missed phrase moves the quality by 0.04, so ranking sixteen configurations on it picks a winner from nothing. The choice rule treats qualities within 0.05 as equal and lets the first-token time decide.

## Results
Two full runs on **`gemma4:12b`** (chat) and **`qwen2.5-coder:7b`** (CSV), Ollama 0.34.2, `nomic-embed-text` and the MiniLM cross-encoder at depth 10 on the CPU, the golden v0 corpus (15 files, 65 chunks) and 8 answerable golden questions asked 3 times under each of the 16 settings (24 runs a point; the p95 of 24 runs is close to the maximum). Result files: `evals/results/s51-run1/` and `evals/results/s51-run2/` (`bench.json`, `report.md`).
- **Run 2 is official** (the guard saw the GPU at 0% busy with 969 MiB in use, the CPU at 4%, a full run, the target profile). **Run 1 is not**: the guard saw the GPU 21% busy before the first section (the desktop; the idle limit is 15%) and the CPU gate failed before one point. The two agree closely.
- **Residency and loads:** every one of the 16 settings had `gemma4:12b` **100% on the GPU** and **0 model loads during questions** in both runs.
- **VRAM** (the product's own server and settings, run 2): nothing of ours loaded 969 MiB; `gemma4:12b` warm **9,306 MiB (934 MiB free)**; `qwen2.5-coder:7b` warm **6,556 MiB (3,684 MiB free)**. Peak during the sweep: 9,104 to 9,320 MiB with an f16 KV cache, **8,892 to 9,071 MiB with q8_0** (about 200 MiB less).
- **The KV-cache type is the one setting that moves speed, in both runs:** the model's median time to first token was **0.33 to 0.39 s with q8_0 against 0.57 to 0.92 s with f16**; question to first token p50 0.68 to 0.76 s against 0.89 to 1.14 s; tokens per second 64 to 67 against 69 to 71 (with q8_0 the first word comes sooner and the text then arrives a little slower; the sittings do not say why). Context size (4,096 or 8,192) and batch size (256 or 512) changed nothing the sittings could tell apart; top-k 3 was faster than 5 under f16 (a shorter prompt: question to first token 0.89 to 0.97 s against 1.10 to 1.14 s) and a little faster under q8_0 (0.68 to 0.71 s against 0.72 to 0.76 s).
- **Quality** (must-include recall over those questions): 0.67 to 0.83, **differences between settings are noise** (one missed phrase moves it by 0.04, and the order of the settings changed between runs). No setting is shown to answer better or worse than another; golden v0 is Claude-authored and easy.
- **Against the SLOs of §6.5 (run 2):** question to first token p50 0.68 to 0.76 s (target 2.5 s), p95 0.88 to 1.67 s (target 4 s), whole turn p95 1.12 to 1.91 s (target 15 s), loads 0: **met under every setting.** **Retrieval plus rerank p95 was 389 to 435 ms against the 400 ms target: met at 5 of 16 points, missed at 11, by at most 35 ms** (run 1: 387 to 446 ms). Retrieval runs on the CPU and does not depend on any swept setting, so this is the CPU and the reranker depth (D-077), not the GPU settings; it is yours to decide with the other deferred items.
- **The choice rule's output** (within 0.05 of the best quality counts as equal): `ctx8192-kvq8_0-batch256-k3` in run 2 (the same family in run 1). **Nothing was changed**: the product ships `ctx8192-kvf16-batch512-k5`. The honest reading: switching the KV cache to q8_0 (`OLLAMA_KV_CACHE_TYPE=q8_0` on your Ollama server, rule R-3 says the sweep chooses it) buys about 0.3 s on the first token and about 200 MiB of headroom, with no quality change visible on 8 easy questions; whether q8_0 hurts long or hard prompts is **not measured**. Your call.
- **At the shipped setting (run 2):** a follow-up question (rewrite, retrieval, first token) 2.05 s p50, 2.33 s p95 against the follow-up target of 5 s; thinking on: question to first token **5.9 s** p50 (6.6 s in run 1), whole turn about 5.9 s, for information; cold rounds (unload, load, first question): 1.5 s from question to first token (run 1, 2 rounds).
- **Ingest speed:** 65 chunks in 6.2 s, **10.5 chunks per second** (embedder on the CPU, a fresh folder).
- **CSV mode (run 2, one run of the 40 questions):** seconds per question **p50 2.8, p95 6.4, max 9.8** (targets 3 and 10), 0 model loads, residency PASS (`qwen2.5-coder:7b` 100% GPU, context 16,384), swaps chat to csv median 2.7 s, csv to chat median 5.0 s (max 5.0; target 6 s), all checks passed; 31 of 40 correct in this single run (C3's 33 of 40 was three runs with the 2-of-3 rule: not comparable, and a check on the copy, not a claim).

## Not verified, stated
- Quality differences between settings (too few questions, easy questions). Long or hard prompts under q8_0. A third sitting or a quieter hour could move the retrieval p95 either way (the CPU gate passed at 4% for run 2). Settings of the user's own Ollama server (flash attention, KV type) were not read, only the private server's; the product's VRAM table is from the user's server as it is configured today. `OLLAMA_NUM_PARALLEL` and flash attention on the user's server are R-3's, unchecked by `doctor`.
- The sweep never exercised an out-of-memory corner (every one of the 16 settings fit): the failure path is tested with fakes only.
