# 04 — CI, branches and pull requests (step S0.5)

## 1. What CI is for
**Continuous integration** means a server runs your checks automatically on every proposed change. You already run `ruff`, `mypy` and `pytest` by hand. CI does it on GitHub's machines, from a clean start, so:
- you can't forget to run them;
- "works on my PC" problems show up (a file you forgot to commit, a package installed once and never recorded);
- a red mark on a pull request blocks the merge, so `v2` stays working.

CI can't run what needs your hardware. Tests marked `live` need Ollama and the GPU, so they stay on your PC (`pytest -m live`).

## 2. GitHub Actions in one page
A **workflow** is a YAML file in `.github/workflows/`. It has:
- `on:` — when it runs (here: pull requests into `v2`/`main`, and pushes to `v2`).
- `jobs:` — independent lists of steps, each on its own fresh machine (`runs-on:`).
- `steps:` — either `uses:` (a ready-made action such as `actions/checkout@v4`, which downloads your code) or `run:` (a shell command).
- `strategy: matrix:` — run the same job several times with different values (e.g. Python 3.12 and 3.13).

YAML is indentation: children are indented under their parent, with spaces, never tabs. Quote values like `"3.10"`, or YAML reads them as the number 3.1.

## 3. Two jobs, two questions
- **windows / lock:** conda builds the env from `environment.yml`, which installs exactly what `requirements/lock-win.txt` pins. *Question: does our real setup still rebuild and pass?*
- **ubuntu / fresh install:** `pip install -e ".[dev]"` resolves the newest versions allowed by the ranges in `pyproject.toml`, on a different OS, with Python 3.12 and 3.13. *Question: does a newer upstream release break us?* A red result here is an early warning, not a disaster.

## 4. Branches and pull requests
A **branch** is a separate line of commits. A **pull request** (PR) says "please merge this branch into that one", and gathers the diff, the discussion and the CI results in one page.
- `main` = v1 until v2 is done; `v2` = where finished steps collect; `step/<id>-<slug>` = one step's work.
- **Squash merge** collapses a branch's commits into one commit on `v2`, so the history reads one commit per step. The final `v2` → `main` uses a **merge commit** instead, keeping every step visible.
- **Branch protection** (a GitHub setting) can require the checks to be green before merging. Without it, the red mark only warns.

## 5. Pinned action versions
`actions/checkout@v4` means "major version 4". Pinning a major version avoids surprise changes. For stricter supply-chain safety you can pin to a full commit SHA; we don't, to keep the file readable, and may revisit it in the security phase.

## Interview-style questions
1. **What can CI catch that your local tests don't?** Missing files, undeclared dependencies, other operating systems and Python versions, and forgetting to run the checks.
2. **Why two different install methods in CI?** The lock proves our exact setup reproduces; the fresh install warns early when upstream changes would break us.
3. **Why squash-merge step branches but merge-commit the final merge?** Squash keeps `v2` readable (one commit per step); the final merge-commit preserves that history in `main`.
4. **Why don't live tests run in CI?** The runners have no GPU or Ollama; those tests run locally on purpose.
5. **What does branch protection add to a green check?** It makes the check mandatory instead of advisory.
