# Evaluation data

This folder holds the data Geekbot is tested on. The code that runs the evaluations lives in `src/geekbot/evals/`.

| Path | What it is | Made by |
|---|---|---|
| `corpus/` | the 15 test documents (the "golden corpus", golden v0) | Claude (original documents, D-067); the Word, PowerPoint and Excel files are generated by `corpus_src/build_office_files.py` |
| `corpus_src/` | the script that builds the office files, and the Word source of the PDF. **Not** part of the corpus | Claude |
| `datasets/golden-questions.md` | the 100 questions of golden v0, as a fill-in template. **The source of truth** | Claude, provisional (D-067) |
| `datasets/golden.jsonl` | the same questions as data, generated from the template | `geekbot eval import`, never by hand |
| `datasets/golden-user.jsonl` | **your** questions, added after the prototype works. Scored on their own, never mixed into v0 | you (not created yet) |
| `datasets/golden-draft.md` | questions drafted by the chat model to copy from. Scratch, git-ignored, **not data** | `geekbot eval generate` |
| `csv/` | results of the CSV analyst mode's evaluation runs (see its own `README.md`) | the runs themselves, from step C3 |

The public benchmark datasets (BEIR SciFact and NFCorpus) are downloaded at runtime by `geekbot eval fetch` into `data/beir/` and are **not** stored here (PLAN.md §9).

## Golden v0: what it is, and what it is not
Golden v0 is **Claude-authored and provisional** (PLAN rev 18, D-067). The documents, the questions and the system have one author, so v0 is easier than real use. Its results are reported as "Claude-authored golden v0, provisional" and are never a headline claim. Your own questions will be the independent set (`golden-user.jsonl`).

The corpus is one fictional 12-person design studio, Brightwater Studio, adopting a local AI assistant called Lantern. Names, dates, prices and incident IDs recur across the files on purpose, so some questions need facts from two or three documents; a few look-alike facts are distractors (for example a 30-day chat-retention proposal that became 90 days). Nothing contradicts anything else. Because the documents are invented, no language model has seen them, so an "unanswerable" question tests grounding, not memory.

## Making the files (once)
In the `geekbot` conda env, from the repository root:

1. `python evals/corpus_src/build_office_files.py` writes the Word, PowerPoint and Excel files into `corpus/` and the memo's Word file into `corpus_src/`.
2. Open `corpus_src/vendor-memo.docx` in Word and "Save as PDF" to `corpus/project/vendor-memo.pdf`. (No PDF library is installed, so this one is by hand.)
3. Commit the generated files with the corpus: they are the data.

`tests/unit/test_golden_corpus.py` builds the office files again, loads all 15 documents through Geekbot's own loaders and checks every question against them (sources exist, every must-include phrase occurs in its sources, every document is used, every item is flagged provisional). If you change a document, rerun step 1.

## Using the golden set
1. `geekbot ingest evals/corpus` indexes the documents. Use this exact folder spelling from the repository root every time: document IDs are hashes of file paths (D-054), so a different spelling is a different set of documents. Run it twice; the second run must say `0 embeddings computed`.
2. `geekbot eval import` reads `datasets/golden-questions.md`, checks it and writes `datasets/golden.jsonl`. It writes nothing while there are errors, and prints each one with its item ID.
3. `geekbot eval validate --check-index` re-checks the JSONL and confirms every source is a ready document in the index (a wrong folder spelling would otherwise show up later as a retriever that finds nothing).
4. `geekbot eval generate` (loads the chat model on the GPU) drafts more questions into `datasets/golden-draft.md`, one per stored passage: useful when you write your own set.

The questions are split into development (40%) and test (60%) items by a fixed rule from each ID (DECISIONS.md D-065), so finish the whole set before anything is tuned and do not renumber afterwards.

## Adding your own questions later
Write them in the same template format (a copy of `datasets/golden-questions.md`, for example `datasets/golden-questions-user.md`) and import them into their own file:

```
geekbot eval import --source evals/datasets/golden-questions-user.md --out evals/datasets/golden-user.jsonl
```

Add your own documents under `corpus/` if you want (re-ingest afterwards). Scoring `golden-user.jsonl` separately from v0 is the ablation harness's job (S2.6); nothing else needs building for it.

## Running the retrieval evaluation (S2.6)
`configs/ablation.toml` configures one run; its results go to `results/<name>/`. The code is in `src/geekbot/evals/` (D-079 explains every choice).

| Path | What it is | Made by |
|---|---|---|
| `configs/ablation.toml` | the run: embedder, reranker, fusion, datasets, sweep grid, bake-off candidates | by hand |
| `results/<name>/rewrites.json` | the cached standalone rewrites of the golden follow-up questions, with the model that made them | `--phase rewrite` |
| `results/<name>/ablation.json` | the ladder R0 to R7 and the leave-one-out variants: means, per-question scores, latency, CPU-gate readings | `--phase ablation` |
| `results/<name>/tuning.json` | the rerank-depth and fusion-candidates sweep on the tuning questions | `--phase tuning` |
| `results/<name>/bakeoff.json` | the embedder and reranker bake-offs | `--phase bakeoff` |
| `results/<name>/abstain.json` | the calibrated abstain threshold, its range, and a check on golden test | `--phase abstain` |
| `results/<name>/report.md` | all of the above as tables, with Δ and its interval; **generated, never edited** | `geekbot eval report` |

```
geekbot eval retrieval --config evals/configs/ablation.toml                 # every phase (CPU-heavy, long; resumes)
geekbot eval retrieval --phase ablation --dataset golden --rung R7          # one piece
geekbot eval report --config evals/configs/ablation.toml                    # the Markdown report
```
Indexes are built in `scratch/ablation/` (git-ignored); the knowledge base in `data/` is never opened. Only the `rewrite` phase uses the GPU (it loads the chat model); everything else runs on the CPU. For a latency number to mean anything the PC must be idle: the run reads the CPU load before and after each timed loop and the report marks a row "(CPU not idle)" when the load never fell to 15%.
